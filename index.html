Editable drone scene, work log

This page records the steps taken toward an editable version of a real drone scene. The scene comes from the MAVREC dataset. The goal is to change the camera viewpoint of a real recording and to insert or move objects inside it without inventing content that has no basis in the real footage. Each row below describes one step, the reasoning behind it, and the papers or repositories used. The right column holds the corresponding video. The rows are ordered in the sequence the work was actually done, including the attempts that did not work, since those results shaped the next step.

Part 1, ReCamMaster

Video 1

This is the original drone footage from the MAVREC dataset. Every other video on this page starts from this clip. The method being followed needs two views of the same scene captured from different camera positions. Only one real view exists for this scene, so the steps below generate a second view artificially.

Video 2

ReCamMaster is a published model for changing the camera viewpoint of an existing video. The reasoning was to test whether a general purpose camera control model could produce the second viewpoint needed here without any extra training. This render rotates the camera by about 20 degrees. The output added a building in the upper right corner. That building does not exist in the real scene. This showed that the model can invent scene content instead of reconstructing what is actually there.

Video 3

The rotation was reduced to about 10 degrees to test whether a smaller camera change would reduce the hallucination seen in Video 2. It did not remove the problem. The model added a glowing structure near the horizon and changed the sky to overcast. Neither of these exists in the original footage. This suggested the hallucination is a property of the model rather than a result of how large the camera change is.

Video 6

CoTracker is a published point tracking model. It was run on the ReCamMaster output from Video 2 to see how object tracking behaves on a render that already contains invented content. This video shows the tracked points moving frame by frame.

Video 7

DEVA is a published tracking and segmentation model. It was used to relocate the tracked object's box on the ReCamMaster render, using the point tracks from Video 6. This shows how a later stage of the pipeline would behave if it were built on top of a render that already hallucinates content.

Part 2, TrajectoryCrafter

Video 4

TrajectoryCrafter takes a different approach from ReCamMaster. It estimates depth with DepthCrafter and reprojects the real pixels of the input video into the new camera position. A generative model is only used to fill the small gaps left behind by that reprojection. The reasoning was that reprojecting real pixels should hallucinate far less than generating every pixel from scratch. This render repeats the same 10 degree rotation used in Video 3. The sky and surrounding structures now match the real scene.
Download

Video 5

A larger combined tilt and pan was applied to check whether the result would hold under a bigger camera change than Video 4. The rendered scene still matched the real one, with no invented structures.
Download

Video 8

This render moves the camera forward instead of rotating it. A forward move should create parallax, where objects close to the camera shift more than distant ones. The roadside sign grows and shifts noticeably while distant trees barely move, which matches real forward motion. A few cars appear and disappear inconsistently across frames. This is a minor artifact from the reprojection and inpainting steps, not a sign of the same hallucination problem seen with ReCamMaster.

Part 4, a training free editing baseline

Video 15

The method being replicated normally uses a trained model to erase an object and redraw it along a new path. This test builds a baseline version of that idea using only classical computer vision, with no training and no diffusion model, to check whether the basic idea is plausible before adding any learned components. The real DEVA box from Video 10 marks the object to remove. A classical inpainting method fills the hole left behind. This video shows that erased result. A visible ghost mark remains where the object used to be.

Part 5, inserting an object that was never in the scene

Video 19

Every edit so far repositioned an object that was already in the scene. This test adds a person who was never in this shot, to check whether the same classical approach extends to insertion and not just repositioning. A real pedestrian was cropped from the original 4K footage, where two people are genuinely visible walking on a nearby path. Real frames of them walking were used so their legs actually move, instead of pasting one static photo repeatedly. The person is marked with a red circle here because they are otherwise easy to miss. At this scale the pasted person did not read as a recognizable human shape.

Part 6, object insertion with a real diffusion model

Video 20

AnyDoor is a published zero shot model for inserting a reference object into a target scene without training on that specific object or scene. The reasoning was that a model built for this exact task should produce a more recognizable shape than the plain photo paste in Video 19. The same person crop was inserted frame by frame using AnyDoor, then blended to remove a border artifact from the raw output. The shape is more recognizable up close than in Video 19, but the person is still small and easy to miss at normal video scale.

Part 7, combining AnyDoor with real tracked motion

Video 21

AnyDoor generates every frame independently, so nothing ties one frame's object shape to the next frame, which limits how consistent a full clip can look. The reasoning here was to run AnyDoor only at a few keyframes and fill the frames between them using real motion instead of new generations. AnyDoor was run at 7 frames spaced across the clip on the real car used in Parts 3 and 4. CoTracker points tracked directly on that real car supplied the scale and shape change between those keyframes, including a perspective effect where the far corner of the car barely moves while the near corner drifts. The frames between keyframes were produced by warping and blending the two neighboring AnyDoor frames using that tracked motion. Some frames roughly halfway between two keyframes show a faint double image from blending two separately warped patches.

Part 8, a video native diffusion model instead of per frame generation

Video 22

Every attempt before this one generated frames independently and stitched them together afterward. VACE is built on the Wan2.1 video diffusion model and generates all 49 frames of a clip in a single pass. The reasoning was that a model with temporal consistency built in should not need any manual stitching. VACE was given the real car crop, the LaMa erased background, and a mask showing where and how large the car should be, all built from real data rather than left to the model's own guess. It was run zero shot on the 1.3B checkpoint with no extra training. The resulting car is sharp and consistent across all 49 frames with no visible seam or flicker, a clear improvement over every earlier attempt. A mistake was found afterward. The text prompt said silver car, but the real reference photo is dark navy. The white car seen here came from the model's own generic guess rather than the actual reference. The shape and consistency result still holds, but the color in this video is not meaningful.

Part 9, grounding size and orientation in real tracked data

Video 23

Video 22's car had a reasonable size and shape but for the wrong reasons. Its scale grew by a fixed formula regardless of where it sat in the frame, and its heading was left for the model to guess. This version fits a real relationship between the original car's screen position and its true pixel size across all 49 unedited frames, and uses that fit to set the size at the new position. It also measures the car's real heading using CoTracker and draws a rotated, car shaped mask instead of a plain square, so the model only has to fill a shape that already points the correct way. This fixed the size. It did not fix the orientation. The model still renders a three quarter angle instead of the flat overhead view the real cars in this footage have, even with a mask shaped and rotated to match the real heading. A stronger prompt asking for a directly overhead view only was tried next. It did not help. It made the model drop the car from the scene instead of changing its pose. PISCO is a newer paper built on the same VACE and Wan backbone, and it solves this exact orientation problem, but only by fine tuning VACE across five stages on about sixteen thousand curated clips with added depth map conditioning. This is a real signal that fixing orientation here needs training, not better prompting or masking.

Part 10, treating the object as its own scene

Video 24

Instead of asking a generative model to invent the car's pose from a mask, this test treats the car as its own small scene and applies TrajectoryCrafter directly to it, the same method already validated for full scenes in Part 2. TrajectoryCrafter's depth estimation needs real motion across multiple frames to work, so a single photo could not be used as input. This video is the real input to that test, a fixed crop that follows the car's own real path across all 49 original frames, before any reprojection.
Download

Video 25

This is the first reprojection result, using a mild forward camera move and no rotation, since the car's real heading stays constant across the clip. The car came out correctly oriented and correctly colored, matching the real cars already in this footage, the first time in this project that orientation came out correct without any hallucination. The result is noticeably blurry up close. The likely cause is that this small crop was scaled up by roughly two and a half times to reach the model's fixed working resolution.
Download

Video 26

The same reprojection was repeated, but fed at the model's native 672 by 384 resolution instead of a small pre cropped window, so no internal upscaling was needed. Sharpness, measured with a fixed Laplacian variance test on a background patch, recovered from about 65 to about 796, close to the original footage's own value of about 936. The car is correctly oriented, correctly colored, and shows no hallucination. This is the strongest result in the project so far, produced by treating the object as a real reprojection problem instead of asking a model to invent its pose.

Part 11, actually moving the car

Video 27

Video 26 proved TrajectoryCrafter could reproject the car cleanly, but it never moved the car to a new screen position, since the camera move used there was a pure forward dolly with no lateral component. A follow up test tried TrajectoryCrafter's own lateral camera controls for this. The car and a fixed background landmark shifted by nearly the same amount in that test, which showed those controls pan the whole camera view together rather than moving one object against a static background, and are not the right tool for this. The working fix returns to compositing. The correctly posed car patch from Video 26 is cropped out, resized to the size a real object would have at its new position, and placed there by blending it onto the erased background. This is the first result in the project where position, size, orientation, and color are all correct at the same time. The blending method used here visibly disturbs a patch of background around the car.
Download

Video 28

This result fixes the background disturbance seen in Video 27 by replacing the blending method with a proper car shaped mask built from brightness segmentation, so only the car's own pixels are touched. The car is also recolored red here. Its real shading and highlights are kept, and only the color itself changes, so this reads clearly as a deliberate edit of the same real car rather than a genuinely different vehicle.

Part 12, a genuinely different car

Video 29

Video 28 is a color change on the same real car, not a different vehicle. This test sources a second, genuinely different car from a separate aerial drone clip filmed from a similarly high, overhead angle. A brightness based tracking and masking approach was tried first and failed, since the surrounding shadow and tree cover in that clip is nearly as dark as the car itself. The fix reused CoTracker to track the car across all 49 frames of that source clip, rejecting any point whose motion did not match the rest of the tracked group. SAM then segmented the car in each frame using both a box prompt and a point prompt together, which fixed a case where a box only prompt had segmented a patch of road instead of the car. A further problem was found by watching the actual result at normal viewing scale rather than a zoomed in crop, where the car looked like a flat rectangle. The real cause was that this car's source patch is taller than it is wide, since it was filmed facing the camera rather than from the side, but it was being resized using width and height targets fit from the first car's own wider shape. Scaling both dimensions independently to the wrong targets squashed a tall object into a short, wide one. The fix scales the patch by one factor in both directions instead, which keeps its own real proportions, and adds a local contrast pass so its highlight detail survives being shrunk to a small size.
